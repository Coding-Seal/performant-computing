# Лаба 10-11

Вариант 1: реализовать барьер для n процессов по принципу дихотомии (recursive doubling), сравнить эффективность с `MPI_Barrier()`.

## Алгоритм

`pow2` — ближайшая степень двойки, не превосходящая `n`, `extra = n - pow2`.

1. **Свёртка.** Процессы с рангом `>= pow2` (их ровно `extra` штук) шлют пустое сообщение процессу `rank - pow2` и блокируются в ожидании сигнала освобождения. Процессы `rank < extra` принимают это сообщение — так n-процессный случай сводится к `pow2`-процессному.
2. **Степенное удвоение.** Первые `pow2` процессов делают `log2(pow2)` раундов: в раунде `k` процесс `i` обменивается пустым сообщением (`MPI_Sendrecv`) с процессом `i XOR 2^k`. После последнего раунда каждый из них точно знает, что все остальные `pow2 - 1` процессов дошли до барьера.
3. **Освобождение.** Процессы `rank < extra` шлют сигнал обратно партнёру из первой фазы (`rank + pow2`), снимая его с ожидания.

Для степени двойки (`extra = 0`) фазы 1 и 3 не нужны, остаётся только степенное удвоение — обычный butterfly-барьер за `log2(n)` раундов. На непростых `n` (проверено на 3 и 5) получается корректный барьер за `floor(log2(n)) + 2` обмена на "лишних" процессах.

Код: `src/barrier_dichotomy.cpp` — сама реализация на точечных обменах, `src/barrier_builtin.cpp` — тонкая обёртка над `MPI_Barrier`. По заданию (п.4) сравниваются только реализации самого барьера, всё вокруг одинаковое: обмены здесь — управляющие сообщения нулевой длины, паковать нечего.

## Замер

`src/main.cpp` (`barrier_benchmark`) прогоняет каждую реализацию барьера 20000 раз подряд и делит суммарное время (`MPI_Wtime`) на число итераций, чтобы убрать шум отдельного вызова (сам по себе он не показателен из-за таймера и планировщика ОС). Замеры сняты через `mpirun --oversubscribe -np N barrier_benchmark 20000` на 2/3/4/5/8 процессах на одной машине — без реальной сети, обмены идут через loopback/shared memory BTL.

| n | dichotomy, мкс/вызов | MPI_Barrier, мкс/вызов | эффективность (Barrier/dichotomy) |
|---|---|---|---|
| 2 | 0.225 | 0.261 | 1.158 |
| 3 | 1.383 | 0.875 | 0.633 |
| 4 | 1.863 | 0.846 | 0.454 |
| 5 | 3.404 | 1.607 | 0.472 |
| 8 | 7.153 | 3.789 | 0.530 |

## Выводы

На `n=2` обе реализации по сути одинаковые (единственный раунд обмена точка-точка против единственного внутреннего обмена в `MPI_Barrier`), и собственная реализация даже чуть быстрее — сказывается отсутствие накладных расходов на диспетчеризацию внутри библиотечной функции.

Начиная с `n=3` `MPI_Barrier()` стабильно быстрее в 1.5-2.2 раза. Основные причины:

- OpenMPI внутри использует более дешёвые низкоуровневые примитивы синхронизации — часто специализированный tree-based или double-ring алгоритм с меньшим числом "тяжёлых" вызовов `MPI_Send`/`MPI_Recv`, либо вовсе в обход очереди сообщений через быстрые пути BTL.
- Реализация на точечных обменах на каждый раунд делает полноценный `MPI_Sendrecv` с проверкой тегов и коммуникатора, плюс для непростых `n` добавляются две дополнительные точечные операции (свёртка/освобождение) — это видно по росту времени между `n=4` (только удвоение) и `n=5` (удвоение + свёртка/освобождение): рост почти вдвое при увеличении числа процессов всего на один.
- `MPI_Barrier` не создаёт объекты `MPI_Status` (здесь они переданы как `MPI_STATUS_IGNORE`), но даже с этим ручная реализация не дотягивает до тюнингованной библиотечной.

Итог: точка-точка версия работает корректно и ведёт себя асимптотически как ожидается (`O(log n)` раундов + `O(1)` на выравнивание непростого `n`), но проигрывает `MPI_Barrier()` по абсолютному времени на всех проверенных `n > 2` — библиотечная коллективная операция лучше оптимизирована под конкретный BTL/транспорт, чем универсальная реализация на голых `Send`/`Recv`.
